imba / showcase

What imba does

imba runs AI coding agents on your own computer and keeps you in charge of them. Here are its 25 main features, each explained in plain words with a film of it at work.

imba is a control room for AI coding agents. You run it on your own computer, open it in a browser or in its apps, and start agents such as Claude Code and Codex on your projects. Each agent works on its own task, and imba shows you which ones are working, which are waiting for an answer from you, and what each one changed.

The point is to stay in charge without watching every step. Agents write a plan before larger work, come back with proof such as films and screenshots, and have their work reviewed, so you check results instead of reading code line by line.

This page walks through 25 features in the order you would meet them, from starting your first agent to leaving work running while you are away.

01 / 25Run agents

Spawns

Run Claude Code and Codex agents side by side on your own machine, each in its own row with its state.

A spawn is one agent at work: Claude Code or Codex, running in one repository on your own machine. Each one sits in its own row under its repository, and its light says whether it is working, waiting on you, holding a plan or done. You start one from the New spawn form with its agent, model and effort, and a spawn can be handed to the other agent with its conversation carried over.

02 / 25Run agents

Ultrafocus

Clear the screen down to the spawns waiting on you, and reach each one by its number.

Ultrafocus clears the screen down to the spawns that are waiting on you, numbered in the order they started waiting. You open one, read the proof it brought back, answer, and you are back on the list. When nothing waits, it lists each repository with the tasks queued for it, so you can pick the next piece of work straight away.

03 / 25Run agents

Editor area

Everything about one spawn in one place: its conversation, the writing area you talk to it from, what it changed, its plan, its log and where it stands.

Opening a spawn shows everything about it in one place. The conversation shows each turn with the cards it ended on, and the State card says what is done and what is left. The writing area under it sends your next message, steers a turn that is still running, or stashes a draft for later. The Explain, Map and Log views show what a turn changed and what the change touches.

04 / 25Check their work

Plans

Read an agent's plan before it builds, comment on any line, send it back, and approve it only when it is right.

Before a spawn builds anything larger, it writes a plan, and its row turns blue. You read the plan in imba, put a note on any line and send it back, and the agent answers with a new version. When the plan is right, you approve it and the agent starts building. A plan for a screen carries a mock of that screen at phone and desktop width.

05 / 25Check their work

Proofs

Every finished change comes back with proof you can see, never only a claim.

A finished change comes back with proof you can look at, not only the agent's word. The proof can be a film of the feature being used at real speed, before and after screenshots of the screen it changed, or a manual test report with one finding per fault. Each opens straight from the card it came on, beside the conversation.

06 / 25Check their work

Feedback mode

Point at what is wrong on a picture, a markdown file or an HTML page, and the note goes back to the agent with it.

Feedback mode lets you point at the thing that is wrong instead of describing it. Turn it on over a screenshot, a markdown file or an HTML page, draw a box or pick a paragraph, and type a note. The notes go to the agent together with the picture or the text they are about, and the agent's next version answers them.

07 / 25Check their work

Reviews

A second set of eyes on every change: reviewers hunt for faults, and mutation tests show whether the tests would notice.

A review puts a second set of eyes on a spawn's change. Reviewers read the change for faults and check it against your rules, the agent fixes what they keep, and the Review card shows each item as fixed. A Codex review has the other agent read the same change. A mutation test plants small bugs in the changed code to show whether the tests would notice.

08 / 25Check their work

Cards

Results arrive as cards you can read at a glance, and you can design your own.

A spawn's results arrive as cards: a trace, a review, a test report or a status, drawn from the source data rather than retold in prose. A trace card opens down to the single call that was slow or failed. You can also design your own card in Settings, block by block, and every agent on the machine can then answer with it.

09 / 25Check their work

Pins

Keep the files, pages and shells a spawn needs on a strip beside it, one key away.

Each spawn has a strip of pins over its writing area: the files, pages and shells it needs. An agent pins the report it wrote or the preview it started, and you can pin your own. A pin opens beside the conversation, so a report, a live page or a running test shell stays in view while you talk to the agent.

10 / 25Agents working together

Loops

Give a task to a builder and a checker that take turns until the work is proven.

A loop gives one task to a builder and a checker that take turns until the work is proven. A planning agent first writes the builder's plan and the checker's plan, which you review as one chart and send back or approve. Then each round the builder builds, the checker tests a fresh copy, and the loop stops only when every check passes.

11 / 25Agents working together

Groups and Organisations

Put a team of agents on one problem and talk only to the one leading it.

A group is a leader spawn with members as spare compute: you talk only to the leader, and it hands parts of the work to the members. An organisation is larger: a Head with leaders under it, each with agents of its own, and roles that change as the work goes. The chart shows who works on what, and asks for more agents wait for your answer.

12 / 25Agents working together

Orchestration

Lay out a run as a graph of workers and judges, and watch each step run and be judged.

An orchestration lays a run out as a graph of stations, the workers that do each step and the judges that pass it or send it back. You review the graph and the server's checks before anything runs. While it runs, the graph and its timeline show which station is working, which was sent back, and where the run waits for you.

13 / 25Agents working together

Software factory

Save a way of working as a reusable shape, and start the next job from it.

A factory is a saved shape for an orchestration: its stations, the agents on each and the lines between them. You draw one in the factory designer, or start from one of the built-in shapes. A new orchestration then picks a factory, so the next job runs the same way without drawing it again.

14 / 25Work that starts by itself

Routines, triggers and automations

Let work start by itself, on a schedule or when something happens.

Work can start without you. A routine is a saved prompt on a schedule, and each run starts its own spawn. A trigger is a check inside a spawn, such as looking at a deploy every ten minutes. An automation chat is one spawn that stays open on the automations row, and its schedules type into it each day.

15 / 25Logins and machines

Accounts

Run spawns across several Claude Code and Codex logins, and new work goes to the login with room.

imba can run spawns under several Claude Code and Codex logins at once. Agent usage shows each login's use of its five hours and its week, and a new login is added and signed in from there. New spawns go to the login with the most room, and when a few logins carry most of the work, imba spreads the spawns across them all.

16 / 25Logins and machines

Machine browser

The agent drives a real browser on the machine while you watch, and you can take over at any moment.

The agent can drive a real browser on the machine, and its chip shows the page live while it works. You watch it type, click and pay as a shopper would. A click on the page takes the wheel from the agent, so you can fix a field yourself and hand it back, and the agent carries on from there.

17 / 25Logins and machines

Support machines

Other computers carry builds and containers, so the main machine stays free.

Support machines are other computers imba can use for builds and containers, so the main machine stays free for the agents. The machine monitor shows each one's processor, memory, load, containers and disks side by side. A spawn's test containers can run on a support machine, and the Docker manager switches to it to show them.

18 / 25Logins and machines

Machine panels

See what the agents cost and what the machine is doing, without leaving imba.

Three panels show what the agents cost and what the machine is doing. Agent usage shows each login's use and where the week's tokens went. The Docker manager lists the containers with their logs and restarts one. The machine monitor shows processor, memory, disks and the processes using them.

19 / 25Other ways in

Pen

Draw an idea or a screen by hand, and the agent reads the drawing.

Some ideas are quicker to draw than to write. The sketch sheet takes a pen or a mouse, and you send the drawing as an idea or as a screen, with a note. An idea comes back as ordered steps the agent starts on. A screen is found in the code and comes back as a mock.

20 / 25Other ways in

Every screen

One server, reached from a desktop app, a phone app or any browser.

imba is one server on your machine. A browser, the desktop app and the phone app all show the same spawns from it. The apps carry no server address: each asks for it once on its first start and loads imba from that server from then on.

21 / 25Everyday work

Alarms

An alert from Grafana comes in, an agent investigates it, and you close it once you have read what it found.

Alerts from Grafana arrive as alarms in imba. From an alarm you start an investigation, a spawn that reads the alarm's figures and logs and reports the cause. Several alarms from the same deploy can go to one investigation together. Once you have read the finding, you close the alarm as resolved.

22 / 25Everyday work

Tasks

Keep coding tasks waiting until there is room for them, and start each as a spawn with one key.

A task is a coding prompt kept for later, filed against a repository until there is room to run it. You queue one from the New spawn form instead of starting it, and agents can file tasks they find along the way. The Tasks list groups them by repository, and a task runs as a new spawn when you are ready.

23 / 25Everyday work

Commit graph

See every branch, worktree and pull request of a repository beside the spawns working on them.

The commit graph draws a repository's history beside the spawns working on it: main, each spawn's branch in its own worktree, and the commits each made. Its pull requests open with their description and changed files. From any commit you can make a new branch in its own worktree and start a spawn on it.

24 / 25Everyday work

Repo map

See a repository's code as a map of its parts and what depends on what, read through a language server.

The repo map draws a repository as a map of its folders, each sized by its code, with lines between the folders that use each other. Opening a folder shows its files and every file elsewhere that imports them, so you can see what a change would touch before an agent makes it.

25 / 25Everyday work

Out of Office

Step away on a schedule: imba mutes its notifications, covers the app with an away screen, and shows only what still needs someone.

Out of Office covers imba with an away screen on a schedule you set. The screen shows only what still needs someone: alarms nobody is on, alarms being handled, and the work still running. You can pause it for a while to work normally, and note a task for later without leaving it.
